Spike 012 — Inngest cross-step engine state

VALIDATED ✓ Architecture decision Phase 7 D-07 needs revision

The question: Phase 7 D-07 prescribed 5 step.run() boundaries. Phase 5's existing runJob uses 1 big step.run("execute"). Inngest's docs say "each step is a separate HTTP request" — on Vercel, that means up to 5 cold starts vs 1. Worth it?

Inngest's execution model (from official docs)

"Each step in your function is executed as a separate HTTP request" "The function is re-executed, this time with the event payload data and the state of the previous execution in JSON."

In production: every step.run() boundary = separate HTTP request from Inngest's runner. On Vercel, that's a Fluid Compute function invocation. Module singletons (enginePool) persist ONLY when the same warm instance handles consecutive requests — opportunistic, not guaranteed.

Recommendation for Phase 7's qbo-ingest: add it to JOB_REGISTRY as a SINGLE entry (mirroring onboarding-import's shape), not as a separate Inngest function with 5 step.run boundaries. The whole gbrain operation runs inside Phase 5's existing runJob.execute step. This pays the cold-start + first-OpenAI tax ONCE per job rather than per phase.

When 5-step shape WOULD be worth it

If an ingest can exceed Inngest's per-step timeout (30s default in serverless, extendable to 5min on paid plans). With spike 007's 1.9s/page rate, that's safe up to ~15 pages per step without batching. SMBs with 1000+ pages need batched step.run boundaries — but split by BATCH (e.g. 10 pages per step), not by PHASE (which is what D-07 prescribed).

Honest caveat: the 11s measurement is the WORST CASE (no Vercel Fluid Compute warm reuse). In production, instance reuse may rescue some cold starts → realistic Shape A wall-clock is more like 6-8s. Shape B's 4.8s stays the same. The real argument for Shape B is predictability, not just speed — Shape B is deterministic; Shape A's wall-clock depends on Vercel's instance-routing luck.

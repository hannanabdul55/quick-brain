VALIDATED ✓ Performance benchmark Phase 4 precondition

The question: On a truly cold Vercel Fluid Compute instance, what is the realistic time-to-first-response for /api/chat? Does Phase 4 need warm-pooling strategies, or is default Vercel behavior good enough?

SURPRISING FINDING: the actual Vercel-cold infrastructure tax (Bun init + module load + Supabase connect) is only ~310ms. The other 1.4s of "cold path" is the first hybridSearch — which is dominated by the OpenAI text-embedding-3-large API roundtrip to embed the user's query. A warm Vercel instance pays the same ~1.2s on every /api/chat call because gbrain has no Q→embedding cache.

Phase 4 implications

  1. Ship without warm-pooling. The 310ms cold tax doesn't justify a scheduled keep-alive cron + the operational complexity it adds. Vercel Fluid Compute's default instance reuse handles 95%+ of requests.
  2. Set realistic chat-UX expectations. Promise "typical 1-2 seconds" not "instant." Show a typing indicator within 200ms (Vercel SSE) so the user knows the system is alive while OpenAI is roundtrip-ing.
  3. Real latency lever (Phase 9+): add a query-embedding LRU cache. Common queries (e.g. "what was weird about last month?") would skip the 1.2s OpenAI call. Could halve warm-path latency.
  4. Don't change serverExternalPackages: ['gbrain']. The 62ms gbrain module-load timing relies on Bun loading raw .ts at runtime. Webpack-bundling gbrain would blow this up.
  5. Cross-validates spike 006 + 007 + 008. Warm path (1.17s mean here) matches spike 006's 1.34s end-to-end measurement. The OpenAI cost class is the same one spike 007 sees per page in importFromContent (1.9s) and the same one Inngest jobs in spike 008 sidestep by using pg_sleep instead. The architectural pattern is consistent across all five v2.0 spikes.

Spike 008 — Inngest concurrency × Supabase free-tier pool

VALIDATED ✓ Performance / load Phase 7 risk closed

The question: Phase 7 fires Inngest jobs with 5 step.run() boundaries each. With M concurrent jobs across tenants, that's up to M×5 effective concurrent queries through the shared gbrain engine (default max: 10 conns). Does the Supabase free-tier pool become a failure mode? At what M does it crack?

Each "job" runs 5 serial pg_sleep(0.05) queries (~250ms ideal serial). M=10 jobs finish in 688ms — basically the same as M=1. The 10 jobs proceed in lockstep through their step.run() chains because each step's 50ms pg_sleep is Postgres-side, not pool-blocking on conn acquisition.

BONUS FINDING — Parameterless executeRaw hangs forever against Supavisor. The first run of this spike included a probe using engine.executeRaw('SELECT pg_backend_pid()') (no params). It hung indefinitely. Reproduced cold AND post-load. Adding any dummy parameter $1 made the same query complete in ~10ms. statement_timeout doesn't fire — the query likely never reaches Postgres at all (stuck in postgres.js's client-side empty-params path). Phase 7 implication: every direct engine.executeRaw call MUST pass at least one parameter. Lint rule recommended.

Pool capacity probe (parameterized)

30 concurrent SELECT pg_backend_pid() AS pid (with $1 sentinel parameter) → 9 distinct Supavisor backends in 71ms gbrain pool max: 10 (default DEFAULT_POOL_SIZE_FALLBACK) 9 distinct backends → confirms max:10 is the ACTIVE wire ceiling, not a singleton, not unlimited. Supavisor recycles backends across transactions ("transaction mode").

Phase 7 implications

  1. No pool tuning needed. Default GBRAIN_POOL_SIZE=10 is sufficient for any realistic v2.0 concurrency. The real Phase 7 latency dominator is the 1.9s OpenAI embedding call (spike 007), not pool contention.
  2. Inngest fanout is safe at M=10. Phase 7's step-divided function (D-07) can fan out to 10 concurrent tenant jobs without pool saturation. 50 effective queries fit through the pool cleanly.
  3. Don't promise hard SLAs in the progress UI. 07-UI-SPEC.md's <JobProgress> phase-labeled stream shouldn't tie to specific timing — at M=10 each step is ~140ms; the embedding step inside ingest is the heavy one.
  4. Lint rule: every engine.executeRaw needs a parameter. Catches the silent-hang footgun at compile time.
  5. Confirms the single-shared-engine architecture. Combined with spike 010 (no cross-tenant leak under 20 interleaved queries), spike 008 proves the cheap one-engine pattern in lib/gbrain/engine.ts is the right architecture for v2.0.

The gbrain runtime-load mechanism (types/gbrain.ts) — why file tracing is a risk:
- `_load(subpath)` does `import(/* webpackIgnore: true */ "gbrain/" + subpath)` —
  a computed specifier the Vercel tracer cannot statically follow.
- `_loadThink()` builds `process.cwd() + "node_modules/gbrain/src/core/think/index.ts"`
  and imports it as a `file://` URL — also untraceable.
- gbrain ships raw `.ts` (no compiled JS); its WASM deps are
  `@electric-sql/pglite`, `tree-sitter-wasms`, `web-tree-sitter`.
- The production server runs as `bun node_modules/.bin/next start` (package.json
  "start" script) so Bun loads gbrain's raw `.ts`. Node would fail with
  ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING.

vercel.json currently exists with the single key `bunVersion` set to `1.x`
(committed in 52be411).

  <decision>
    The in-process gbrain fix depends on the server running under Bun: gbrain

    in Vercel's own runtime — `vercel.json` already has `bunVersion`, but that
    governs the install step / Bun version, not necessarily the function runtime.
    Before deploying, decide how Vercel functions execute the gbrain path.
  </decision>
  <context>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| git repo → Vercel build | Source crosses into Vercel's build environment |
| Vercel encrypted env config → function runtime | Secrets are decrypted and injected into the running function |
| public internet → deployed routes | Anyone can reach `/`, `/api/health`, `/api/tenants/*` |
| build step → Sentry SaaS | Source maps uploaded with `SENTRY_AUTH_TOKEN` |

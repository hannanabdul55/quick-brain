<objective>
Take the build-verified app (04-01) with its health endpoint and Sentry
instrumentation (04-02) and deploy it to Vercel at a real public URL. Load every
secret into Vercel's encrypted env config, deploy via the Git integration
(push-to-main → build), and verify the live result end-to-end: `/api/health`
returns 200 with three green subsystems, and a deliberate server error plus a
deliberate client error both land in the Sentry dashboard.

This plan also handles the two RESEARCH.md-flagged risks: it verifies
`OPENAI_API_KEY` / `ANTHROPIC_API_KEY` actually exist before deploy (Assumption
A3, HIGH risk — without them the deploy "succeeds" but chat silently returns
empty answers), and it documents the Hobby-tier compliance + Pro-upgrade decision
using the *current* Vercel limits (300s default function timeout — DEPLOY-05's
"60s timeout" framing is obsolete per RESEARCH.md Pitfall 2).

`RESEND_API_KEY` is named in DEPLOY-02's criterion but is a Phase 6 precondition
with no value yet — this plan sets up the env-var *mechanism* and adds every
secret that exists today; Resend is added later by Phase 6 via the same workflow.

Purpose: This is the phase's terminal plan — it makes the app real (DEPLOY-01),
gets every secret into encrypted config (DEPLOY-02), proves observability works
live (DEPLOY-04), and records the cost-tier decision (DEPLOY-05). It depends on a
verified build (04-01) and a complete observability layer (04-02).
Output: A live deployed app at a `vercel.app` URL, a populated Vercel env config,
a committed `.env.example` key inventory, and `docs/deploy.md` with the
Pro-upgrade decision record.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| repo → Vercel build | committed code and `.env.example` cross into the build platform |
| operator → Vercel env config | secrets are entered via `vercel env add` and encrypted at rest |
| Vercel env config → function runtime | `process.env` is populated only at build/runtime, not in the repo |
| public internet → deployed app | the live `vercel.app` URL is reachable by anyone |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-10 | Information Disclosure | a secret committed to git (`.env.local`, `SERVICE_ROLE_KEY`) | mitigate | `.gitignore` already excludes `.env*` and `.vercel`; Task 2's audit asserts `git ls-files | grep -E '\.env'` returns only `.env.example`; Task 3's acceptance check confirms no secret value appears in `.env.example` or any response. Severity: high if unmitigated — mitigated. |
| T-04-11 | Information Disclosure | secrets stored in Vercel env config | accept | Vercel encrypts env vars at rest and `vercel env add` defaults production values to encrypted-and-unreadable; the app only reads `process.env` at runtime. Standard platform control — accepted. |
| T-04-12 | Information Disclosure | the deployed `/api/health` leaking a connection string or secret | mitigate | The probe payload (built in 04-02) returns booleans + latency + sanitized detail only; Task 3's acceptance check confirms no secret appears in the live response body. |
| T-04-13 | Information Disclosure | `SENTRY_AUTH_TOKEN` exposed at runtime/client | mitigate | `SENTRY_AUTH_TOKEN` is added as a plain (non-`NEXT_PUBLIC_`) Vercel env var used only by `withSentryConfig` at build time; `.env.example` documents it as build-time only. |
| T-04-14 | Spoofing | the public deployed URL with no auth | accept | Phase 4 has no auth (auth is Phase 6); the deployed app exposes only the demo seed tenant and a secret-free `/api/health`. Acceptable for this phase — Phase 6 (AUTH) gates the door. RESEARCH.md Security Domain V2/V4 confirms. |
| T-04-15 | Tampering | a stale/missing secret causing a silently-broken deploy | mitigate | Task 1 verifies `OPENAI_API_KEY`/`ANTHROPIC_API_KEY` exist before deploy (Assumption A3); Task 3 uses `/api/health` (three green subsystems) as the live completeness check for DEPLOY-02. |
| T-04-SC | Tampering | package installs during this plan | accept | This plan installs no new package — `@sentry/nextjs` was installed and legitimacy-gated in 04-02. Vercel's `bun install` fetches the already-SHA-pinned `gbrain` git dependency. |
</threat_model>

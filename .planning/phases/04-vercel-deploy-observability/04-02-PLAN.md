<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| public internet → `/api/health` | `/api/health` is unauthenticated by design; anyone can call it |
| Vercel function → Supabase Postgres | the DB probe opens a throwaway connection using a secret URL |
| Vercel function → Supabase Storage | the storage probe issues a HEAD with the service-role key |
| Vercel function → Sentry SaaS | captured error events leave the trust boundary to a third party |
| build step → Sentry SaaS | `withSentryConfig` uploads source maps using `SENTRY_AUTH_TOKEN` |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-04 | Information Disclosure | `/api/health` JSON response | mitigate | Probe returns `{ ok, latencyMs, detail }` only — no connection string, no version, no host. Probe `detail` on failure is a sanitized generic message; `probes.test.ts` asserts no `postgres://`-shaped substring leaks. Severity: high if unmitigated — mitigated. |
| T-04-05 | Information Disclosure | Sentry event payload (server + client) | mitigate | Each Sentry config has a `beforeSend` that strips cookies/auth headers and env-shaped values; the app already logs metadata-only and never passes `process.env` or question text into captured context. Severity: high if unmitigated — mitigated. |
| T-04-06 | Information Disclosure | `SENTRY_AUTH_TOKEN` leaking into the client bundle | mitigate | `SENTRY_AUTH_TOKEN` is used only inside `withSentryConfig` in `next.config.ts` (build-time); it is NOT `NEXT_PUBLIC_`-prefixed. Only `NEXT_PUBLIC_SENTRY_DSN` reaches the client and a DSN is not a secret. |
| T-04-07 | Denial of Service | `/api/health` cost amplification | mitigate | Probes are reachability checks (`SELECT 1`, storage HEAD) — never an LLM `think()` call. Each probe is wrapped in a ~2.5s `withTimeout` so a hung subsystem cannot stall the endpoint or accumulate cost. |
| T-04-08 | Denial of Service | DB probe exhausting the shared engine pool | mitigate | `probeGbrainDb` uses a throwaway `postgres` connection closed immediately; it never calls `createGBrainEngine`, so it cannot poison or exhaust the app's `enginePool`. |
| T-04-09 | Elevation of Privilege | `SUPABASE_SERVICE_ROLE_KEY` (bypasses RLS) reachable from client | accept | The storage probe runs server-side in a `runtime = "nodejs"` Route Handler; `lib/storage/` is already server-only with raw `fetch`. No new client exposure introduced. |
| T-04-SC | Tampering | `@sentry/nextjs` package install | mitigate | Task 1 is a blocking-human legitimacy checkpoint verifying `@sentry/nextjs` against npmjs.com before install; version pinned in `package.json`. `[ASSUMED]` package per RESEARCH.md — checkpoint is not auto-approvable. |
</threat_model>

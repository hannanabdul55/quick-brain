<objective>
Wire the generic job runner end-to-end: the one Inngest function that runs any registered operation, the POST trigger route that creates a job and dispatches it, and the GET status route the browser polls. After this plan a job can be triggered over HTTP, run out-of-band in an Inngest worker invocation, and be observed through its `app.jobs` row.

Purpose: This is JOBS-01 (long ops run as background jobs, not inline) and the server half of JOBS-02 (browser sees progress via polling). The generic kind-agnostic shape (D-05) means Phase 7's QBO ingest plugs in by adding a registry entry only — no trigger/worker/status changes.
Output: `lib/inngest/functions.ts`, edits to `app/api/inngest/route.ts`, `app/api/jobs/route.ts`, `app/api/jobs/[id]/route.ts`.
</objective>

    Create `lib/inngest/functions.ts`. Export `runJob = inngest.createFunction(...)` with:
    - config `{ id: "run-job", retries: 1 }` — `retries: 1` because `gbrain import` /
      `runOnboarding` is NOT idempotent; re-running from scratch double-imports (Pitfall 3).
      Do NOT raise the retry count.
    - trigger `{ event: "app/job.requested" }`.
    - handler `async ({ event, step }) => {...}` reading `event.data` as
      `{ jobId: string; kind: keyof typeof JOB_REGISTRY; params: Record<string, unknown> }`.

    Handler body: `await step.run("mark-running", () => setRunning(jobId))`. Then a try/catch:
    inside try, `const result = await step.run("execute", async () => { const op =
    JOB_REGISTRY[kind]; return op(params, (p) => updateProgress(jobId, p)); })` — the
    `updateProgress` progress writes happen INSIDE the operation as plain awaits, NOT wrapped
    in `step.run` (steps are memoized and replayed — a progress write is a transient
    side-effect). Then `await step.run("mark-done", () => finishJob(jobId, result))`. In
    catch, `await step.run("mark-error", () => failJob(jobId, String(err)))` then `throw err`
    so Inngest records the failure. This mirrors `orchestrator.ts`'s one-try/catch-with-
    terminal-events shape.

    Edit `app/api/inngest/route.ts`: import `runJob` from `@/lib/inngest/functions` and add
    it to the `serve({ client: inngest, functions: [runJob] })` array (it was `[]` from plan 05-01).
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser -> POST /api/jobs | Untrusted request body crosses into a Route Handler before a DB write and an Inngest event send |
| Browser -> GET /api/jobs/[id] | The status route returns job state (`result`, `error`) to the browser |
| Inngest cloud -> /api/inngest -> runJob | Inngest invokes the serve route to execute the generic function |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-09 | Denial of Service | `app/api/jobs/route.ts` (unauthenticated pre-Phase-6) | accept | Pre-Phase-6 the trigger route has no auth. Inngest free tier caps at 50k executions/month; a runaway loop could exhaust it. Accepted for Phase 5: the route is exercised only by the demo/seed flow, `retries: 1` caps per-job executions, and Phase 6 gates the route behind a session. A comment in the route records this. Phase 6 (AUTH-06) closes it |
| T-05-10 | Tampering / Spoofing | `app/api/jobs/route.ts` input | mitigate | The body is zod-validated by `jobRequestSchema` before `createJob` or `inngest.send`; an unknown `kind` is rejected against the registry enum (Security V5). `createJob` writes `params` via parameterized SQL (`sql.json`) — covered by T-05-05 in plan 05-03 |
| T-05-11 | Information Disclosure | `app/api/jobs/[id]/route.ts` response | mitigate | The status route returns only `status`, `progress`, `stage`, and (terminally) `result`/`error`. `params`, `created_at`, and raw DB columns are never returned. `result` is a small structured `{ tenantId }`; `error` is already sliced + sanitized by `failJob`. No stack trace or DB internals reach the browser (Security V7) |
| T-05-12 | Information Disclosure | `app/api/jobs/route.ts` logging | mitigate | `console.log` records only `kind` and `jobId`, never `params` — `params` may carry PII. Mirrors `tenants/route.ts` log-only-slug precedent |
| T-05-13 | Spoofing | `app/api/inngest/route.ts` (runJob now registered) | mitigate | `INNGEST_SIGNING_KEY` (documented in plan 05-01) makes `serve()` verify the HMAC signature on every inbound request, so only Inngest can invoke `runJob`. No change needed here — registering the function does not weaken the existing signature check (T-05-01) |
| T-05-SC | Tampering | npm/package installs | accept | This plan installs no packages — all dependencies (`inngest`, `postgres`, `zod`) are already installed by prior plans. No supply-chain surface |
</threat_model>

  GET /api/jobs/[id] -> 200 { status, progress, stage, result?, error? }
                       status: "queued" | "running" | "done" | "error"

Existing client-component analogs (copy the shape):
  components/onboard/onboarding-progress.tsx — "use client"; props { stage, label,
    progress (0..1), allStages: StageItem[] }; 8px (`h-2`) progress-bar track with
    role="progressbar" + aria-valuenow/min/max; stage checklist with isDone (green
    check &#10003;) / isCurrent (Loader2 animate-spin) / isPending (muted dot);
    16x16 (`h-4 w-4`) icon slot. THE 8px TRACK + transition-all duration-500 MUST be
    copied verbatim — UI-SPEC requires polling and SSE progress to look identical.
  components/onboard/error-banner.tsx — ErrorBanner, reused AS-IS for the error state.
  app/onboard/page.tsx — useRef holds the long-lived browser resource (there an
    EventSource), useEffect return cleans it up; terminal handler stops the loop.
  components/ui/badge.tsx — Badge; use variant="secondary" for "Queued"/"Running"/
    "Still working" — NEVER variant="destructive" for a healthy job.

UI-SPEC locked specifics:
  - Poll interval ~2s. Bounded loop — max-attempts cap, NO unbounded setInterval.
  - States: queued (muted dot, 0% bar, "Queued" badge, helper "Getting things ready…"),
    running (bar fills, spinner, climbing tabular-nums "{n}% complete"), slow-but-healthy
    (after ~20s of no new stage: "Still working" badge + line "This is taking a little
    longer than usual — your data is safe and we're still on it."), done (100% bar, all
    green checks, primary Button "View results"), error (ErrorBanner: "Something went
    wrong while we were setting things up." + "Try again" outline button — show the
    sanitized server `error` only as a secondary muted line), poll give-up ("This is
    taking longer than expected." + "Check again" — neutral, NOT red).
  - Onboarding/import stage labels are the locked five: "Creating your brain", "Reading
    your invoices and emails", "Building the knowledge graph", "Indexing for search", "Ready".
  - Accessibility: keep role="progressbar" + aria-value*; announce stage/terminal
    transitions via an aria-live="polite" region; the spinner is decorative — text + aria
    carry "running".
  - No raw job IDs, no stack traces, no "Inngest"/"serverless"/"timeout" in the happy path.

  <action>
    Create `lib/jobs/use-job-status.ts` — a `"use client"` React hook `useJobStatus(jobId:
    string | null)`. It runs a BOUNDED poll loop: a `setInterval` (~2000ms) held in a
    `useRef`, started in a `useEffect` keyed on `jobId`, and torn down in the `useEffect`
    return (mirrors `app/onboard/page.tsx`'s `eventSourceRef` + cleanup). Each tick does
    `fetch('/api/jobs/' + jobId)` and parses the `{ status, progress, stage, result, error }`
    JSON.

    Stop conditions (clear the interval): `status === "done"`, `status === "error"`, OR a
    max-attempts cap is reached (compute the cap from a target soft-timeout — e.g. ~150
    attempts at 2s ~= 5 min — define it as a named constant). On hitting the cap with the
    job still running, surface a distinct `"timed-out"` UI state (NOT an error — the job
    may still be running server-side).

    Return an object the component renders from: at least `{ status, progress, stage,
    result, error, pollState }` where `pollState` is one of `"polling" | "stopped" |
    "timed-out"`. Also return a `restart()` function that resets attempts and re-arms the
    interval (drives the "Check again" action). Never leave an interval running after the
    component unmounts or a terminal state is reached.
  </action>

  </verify>
  <acceptance_criteria>

    - There is a named max-attempts constant; the loop stops on `done`, `error`, or the cap.
    - Hitting the cap surfaces a `"timed-out"` poll state distinct from `error`.
    - The hook returns `status`, `progress`, `stage`, `result`, `error`, a poll-state
      indicator, and a `restart()` function.
    - `bunx tsc --noEmit` passes.
  </acceptance_criteria>

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-14 | Information Disclosure | `components/jobs/job-progress.tsx` rendered output | mitigate | The component renders only `status`, `progress`, `stage`, sanitized `error`, and a small structured `result`. The UI-SPEC Copywriting Contract forbids raw job IDs, stack traces, and the words "Inngest"/"serverless"/"timeout" in the happy path; the error state shows the already-sanitized server `error` only as a secondary muted line. No DB internals or secrets reach the DOM |
| T-05-15 | Denial of Service | `lib/jobs/use-job-status.ts` poll loop | mitigate | The poll loop is bounded — a named max-attempts cap and a `setInterval` cleared on `done`/`error`/cap and on unmount. No unbounded `setInterval`; a hung job degrades to a neutral "timed-out" state rather than hammering the DB or leaking timers (RESEARCH Don't Hand-Roll) |
| T-05-16 | Spoofing | deployed `app/api/inngest/route.ts` | mitigate | `INNGEST_SIGNING_KEY` set in Vercel encrypted env config -> `serve()` verifies the HMAC signature on every inbound request, so only Inngest can invoke `run-job` on the public deployed route. Task 3 confirms the route responds correctly under the `bun@1.2.0` runtime |
| T-05-17 | Information Disclosure | `INNGEST_EVENT_KEY` / `INNGEST_SIGNING_KEY` in production | mitigate | Both stored in Vercel encrypted env config (manual env-var path, matches DEPLOY-02); never `NEXT_PUBLIC_`-prefixed and never referenced in `lib/jobs/use-job-status.ts` or `components/jobs/job-progress.tsx` (client code). Documented as server-only in plan 05-01's `.env.example` edit |
| T-05-SC | Tampering | npm/package installs | accept | This plan installs no packages — `inngest` was installed (and human-verified) in plan 05-01; no new shadcn primitive is added. No supply-chain surface |

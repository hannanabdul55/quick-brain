# Phase 5 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Scope

This phase's UI surface is **one thing**: a background-job progress indicator that shows a polled job's stage and percentage so there is never a silent multi-minute wait (Success Criterion 3 / JOBS-02).

It is **not** a new page, dashboard, navigation, auth screen, or QuickBooks-connect UI. It is a progress component plus its three visible states (running, success, error) and a "long-running but healthy" reassurance treatment.

**Coexistence rule (CONTEXT.md D-02):** the existing SSE-driven onboarding "theater" (`components/onboard/onboarding-progress.tsx`, `lib/onboarding/sse.ts`) stays for *inline* operations. Phase 5 adds a *polling*-driven job-progress surface for cross-function background jobs. The two MUST be visually indistinguishable to the user — same progress-bar geometry, same stage-checklist treatment, same color language. The browser does not know or care whether progress arrives via SSE or polling; the design contract is identical so a job feels exactly like onboarding.

**Source of truth for visuals:** the existing `OnboardingProgress` component is the established pattern. This contract codifies it and extends it for the polling lifecycle (queued, timeout-soft-warning). The executor SHOULD build the job-progress component by generalizing `OnboardingProgress`, not inventing a new look.

## Spacing Scale

Declared values (multiples of 4 — matches Tailwind v4 default scale already used across `app/onboard/page.tsx` and `components/onboard/`):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gap inside a stage row (`gap-1`), inline padding |
| sm | 8px | Stage-checklist row spacing (`space-y-2`), icon gaps (`gap-2`) |
| md | 16px | Default block spacing inside the progress card (`space-y-4`), error-banner padding (`p-4`) |
| lg | 24px | Card content padding (shadcn `Card` default) |
| xl | 32px | Gap between the progress card and surrounding page content |
| 2xl | 48px | Major vertical breaks (not expected this phase — single component) |
| 3xl | 64px | Page-level spacing (not expected this phase) |

Exceptions:
- **Progress-bar track height: 8px** (`h-2`). This is a fixed component dimension, not a spacing token — it matches the existing `OnboardingProgress` track exactly and MUST stay 8px so polling progress and SSE progress look identical.
- **Stage indicator slot: 16px × 16px** (`h-4 w-4`) for the spinner / check / dot — matches `OnboardingProgress`.

## Typography

The progress surface carries text only — no display headings. Three roles, two weights. Sizes map to Tailwind classes already in use across the onboarding components.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Card title (job name / current stage label) | 16px (`text-base`) | 600 (semibold — `CardTitle` default) | 1.2 |
| Body / stage-checklist rows | 14px (`text-sm`) | 400 regular; 500 medium for the *current* stage and error messages | 1.5 |
| Percentage / count caption | 14px (`text-sm`) | 500 (medium) — tabular numerals (`tabular-nums`) so the number does not jitter while it climbs | 1.5 |
| Meta / badge label ("Running", "Queued", "Taking longer than usual") | 12px (`text-xs`) | 500 (medium — `Badge` default) | 1.4 |

Two weights only: **regular 400** and **medium/semibold 500–600**. `CardTitle` renders semibold (600); body emphasis uses medium (500). No third weight.

Rationale: this is exactly the type ramp the existing `OnboardingProgress` and `ErrorBanner` already use (`text-sm`, `font-medium`, `CardTitle`). The phase introduces no new typographic role.

## Color

The app is a monochrome neutral system (OKLCH variables in `app/globals.css`, `neutral` base color). There is **no chromatic brand accent** — primary is near-black. Progress communicates state through neutral fill plus two reserved semantic colors (success green, destructive/error red), exactly mirroring `OnboardingProgress` (green check) and `ErrorBanner` (red).

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--background` `oklch(1 0 0)` (white) | Page background, card surface |
| Secondary (30%) | `--card` / `--secondary` / `--muted` `oklch(0.97 0 0)` (near-white) | Card chrome, progress-bar **track**, pending-stage dots, skeleton |
| Accent (10%) | `--primary` `oklch(0.205 0 0)` (near-black) | Progress-bar **fill**, current-stage spinner, percentage number, primary action |
| Success | `text-green-600` | Completed-stage check mark **and** the job-success state icon/heading only |
| Destructive / Error | `--destructive` `oklch(0.577 0.245 27.325)` + `bg-red-50 / border-red-200 / text-red-900` | Error-state banner and error icon only |

Accent reserved for: the progress-bar fill, the current-stage `Loader2` spinner, the live percentage number, and the single primary button (e.g. "View results" / "Try again"). The accent is NOT applied to pending stages, body copy, the track, or the card border.

Semantic color is reserved strictly: **green** appears only on a completed step or the terminal success state; **red** appears only on the terminal error state. A *running* or *queued* or *slow-but-healthy* job uses neutral accent only — a long wait must never look like an error.

State-to-color contract:

| Job state | Indicator | Color |
|-----------|-----------|-------|
| `queued` | Static neutral dot or muted spinner, 0% bar | Secondary (muted) — not accent yet |
| `running` | `Loader2` spinning, bar fills | Accent (near-black) fill + spinner |
| `running` (slow — see Copywriting) | Same spinner + reassurance line | Accent — still neutral, NOT red |
| `done` | Check mark, bar at 100% | Success green check; bar fill stays accent |
| `error` | Error banner | Destructive red |

## Interaction Contract — the job-progress lifecycle

The browser polls `GET /api/jobs/[id]` (CONTEXT.md D-02). The component is a client component driving a bounded poll loop. The visible contract:

| Phase | What the user sees | Behavior |
|-------|--------------------|----------|
| **Optimistic start** | Progress card appears immediately on trigger with the bar at 0% and the first stage labelled, before the first poll returns | No blank gap between clicking and seeing progress. Card renders on the `202 Accepted` / `jobId` response. |
| **Queued** | Card title shows the operation name; bar at 0%; a `Badge` reads "Queued"; first stage row shows a muted (non-spinning) indicator | Covers the gap between job creation and the Inngest worker picking it up. |
| **Running** | Bar fills smoothly (`transition-all duration-500`); current stage row shows the spinning `Loader2`; completed stages show the green check; pending stages show the muted dot; percentage caption climbs with `tabular-nums` | Poll interval ~2s (Claude's discretion per CONTEXT.md; 2s recommended — frequent enough to feel live, light on the DB). Bar width animates between polls so it never jumps. |
| **Slow but healthy** | After a threshold of continuous running with no new stage (recommend ~20s), a calm reassurance line appears below the bar; the `Badge` may switch to "Still working" | This is the explicit anti-silent-wait treatment. It is reassuring, neutral-colored, never red. The spinner keeps spinning so the UI never looks frozen. |
| **Success** | Bar snaps to 100%; all stage rows show the green check; a single primary `Button` becomes available (e.g. "View results") | Polling stops on `status: done`. No auto-jankiness — the success state is stable and legible. |
| **Error** | The `ErrorBanner` pattern: red banner, plain-language message, outline "Try again" button | Polling stops on `status: error`. Error copy is the *sanitized* `error` string from the status route — never a raw stack trace or job ID (Research §Security V7). |
| **Poll give-up** | If the poll loop hits its max-attempts cap with the job still running, show a neutral (not red) "this is taking longer than expected" message with a "Check again" action | Bounded poll loop — never an unbounded `setInterval` (Research §Don't Hand-Roll). This is a soft timeout, not a failure: the job may still be running server-side. |

Accessibility (carry forward from `OnboardingProgress`, do not regress):
- The progress bar MUST keep `role="progressbar"` with `aria-valuenow` / `aria-valuemin` / `aria-valuemax`.
- Stage transitions and the terminal success/error states SHOULD be announced via an `aria-live="polite"` region so a screen-reader user is not left in a silent wait either.
- The spinner is decorative — it MUST NOT be the only signal of "running"; the text label and `aria-live` updates carry it.

## Copywriting Contract

Audience: non-technical small-business owners. Copy is plain, calm, and reassuring. **No raw job IDs, no stack traces, no "Inngest", no "serverless", no "function timeout" in the happy path.** Numbers and a clear stage label carry the UI.

| Element | Copy |
|---------|------|
| Primary CTA | **"View results"** (on job success — takes the user to whatever the job produced). For the onboarding/import consumer this is the existing "go to dashboard" navigation; the button label stays outcome-focused, not job-focused. |
| Queued-state label | Badge: **"Queued"** · helper line: **"Getting things ready…"** |
| Running-state stage labels | Reuse the operation's own human stage labels. For onboarding/import (the D-05 first consumer) the locked labels are the existing five: "Creating your brain", "Reading your invoices and emails", "Building the knowledge graph", "Indexing for search", "Ready". A generic job with no stage labels falls back to a single label: **"Working on it…"** |
| Percentage caption | **"{n}% complete"** (e.g. "60% complete"). Omit entirely if a job reports no percentage — show the stage label alone rather than a fake number. |
| Slow-but-healthy reassurance | Badge: **"Still working"** · line: **"This is taking a little longer than usual — your data is safe and we're still on it."** (Neutral tone, present-progressive, reassuring. Never implies failure.) |
| Empty state heading | **"No job running"** |
| Empty state body | **"Start an action and you'll see live progress here."** (Only relevant if the progress surface is ever rendered with no active job — e.g. a stale link. Not expected in the primary onboarding flow.) |
| Error state | Heading/message: **"Something went wrong while we were setting things up."** Body / next step: **"Your data is safe. Try again, and if it keeps happening, give it a few minutes."** Action: **"Try again"** (outline button — matches `ErrorBanner`). The sanitized server `error` string MAY be shown as a secondary muted line, but the primary message is always plain language. |
| Poll give-up message | **"This is taking longer than expected."** Body: **"It may still be finishing in the background."** Action: **"Check again"** (re-starts the poll loop — neutral, not a retry of the job). |
| Destructive confirmation | **None.** Phase 5 introduces no destructive action. The job-progress surface only *observes* a job; it does not cancel, delete, or reset anything. (Note: `components/insights/reset-button.tsx` exists from the v1.0 hackathon demo and is slated for removal in Phase 9 CLEAN-01 — Phase 5 must not add to it or build any new destructive control.) |

Tone rules for the executor:
- "We" / "your" framing — partner voice, not system voice ("we're setting things up", not "job executing").
- Present progressive for in-flight states ("Reading…", "Working…", "Still working").
- A long wait is described as *normal and safe*, never as a problem.
- Error copy always pairs the problem with a calm next step and a reassurance that data is safe.

## Component Inventory (for the planner)

The phase needs **one** new client component plus supporting wiring. No new shadcn primitives.

| Component | Type | Built from | Notes |
|-----------|------|------------|-------|
| `JobProgress` (working name) | New client component | Generalize `components/onboard/onboarding-progress.tsx` | Renders the lifecycle states above from a polled job row (`status`, `progress`, `stage`, `result`, `error`). Same 8px bar, same stage-checklist treatment, same color contract. |
| Poll hook (e.g. `useJobStatus`) | New client hook | — | Bounded poll loop (~2s interval, max-attempts cap, backoff) against `GET /api/jobs/[id]`. Stops on `done`/`error`. Surfaces a soft-timeout state. Not a visual component but it drives every state transition above. |
| `ErrorBanner` | Reused as-is | `components/onboard/error-banner.tsx` | The job error state SHOULD reuse this exact component for visual consistency. |
| `Badge` | Reused | `components/ui/badge.tsx` | "Queued" / "Running" / "Still working" status pill. Use `variant="secondary"` (neutral) — never `destructive` for a healthy job. |

The existing `OnboardingProgress` MAY be refactored so onboarding and job progress share one component, or `JobProgress` MAY be a sibling that copies the visual contract. Either is acceptable; the hard requirement is that the two are visually identical to the user.
